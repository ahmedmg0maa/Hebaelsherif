## ما تم تنفيذه

### 1. الأمن والهوية

- ترقية Next.js إلى `16.2.11` وتحديث lockfile ووضع overrides للثغرات العابرة؛ `pnpm audit --prod` لا يعرض ثغرات معروفة.
- إزالة اعتماد دخول الإدارة على بريد واحد مشترك. كل مديرة تدخل ببريد حسابها وكلمة مرورها، ثم يُعاد فحص الدور وAAL2.
- تسجيل محاولات الدخول والنجاح والحظر وMFA وإنشاء/انتهاء/إلغاء الجلسات والخروج، دون حفظ IP أو User-Agent خام أو كلمة مرور أو token.
- إنشاء خروج إداري صريح يلغي الجلسة الحالية ويمسح cookie ويسجل الحدث.
- تحويل CSP للسكريبتات من inline عام إلى nonce فريد لكل طلب مع `strict-dynamic` و`script-src-attr 'none'`، وربط nonce بسكريبت الثيم وJSON-LD.
- جعل preview token أحادي الاستخدام ذريًا داخل PostgreSQL، بما يغلق سباق القراءة/التحديث وإعادة الاستخدام.
- توسيع فحص الأرشيف ليقرأ ZIP وTGZ متداخلين، ويرفض `.env` و`supabase/.temp` والمفاتيح الخاصة ونسخ قواعد البيانات وآثار الاختبار.

### 2. إغلاق صلاحيات قاعدة البيانات

Migration `080_security_login_history_and_preview_tokens_local_only.sql`:

- يقيد `is_enrolled` بالمستخدم نفسه أو Service Role أو مدير تعلّم مصرح.
- يسحب تشغيل `expire_stale_orders` من `public/anon/authenticated` ويجعله server/scheduler only.
- يمنع browser roles من إدراج/تعديل/حذف `audit_logs` و`admin_security_events`؛ السجل append-only عبر الحدود المحكومة.
- يضيف الحقول والفهارس والقيود اللازمة لأرشيف تسجيل دخول محدود البيانات.
- يضيف الاستهلاك الذري service-only لرموز المعاينة.

Migration `081_admin_roles_analyst_auditor_local_only.sql`:

- يضيف `analyst` و`auditor` إلى الأدوار المحكومة.
- يحافظ على منع تعديل الدور الذاتي، منع إزالة آخر owner، وقصر إدارة الأدوار على owner مع صلاحية `roles.manage`.
- يحافظ على تنفيذ تغيير الدور/الصلاحيات والتدقيق كمعاملة واحدة.

- إظهار حالات منفصلة: unconfigured، migration-required، error، وready بدل الادعاء بعدم وجود بيانات.

## التحقق المنفذ

نجح ما يلي:

- `type-check`
- `lint`
- `audit --prod --audit-level=moderate` — لا ثغرات معروفة
- production `build:isolated` — 71 صفحة
- كل عقود الحوكمة المحلية الخاصة بالحجز والدفع والكتالوج والمحتوى والوسائط والأدوار والجلسات والتسليم المحمي والحسابات
- `audit:routes`, `audit:ux`, `audit:colors`, `audit:security`, `audit:admin`, `audit:media`, `audit:commerce`, `audit:catalog`, `audit:booking`, `audit:db`, `audit:launch`
- فحص ZIP/TGZ النهائي بعد فكّه والبحث داخله عن الأسرار والمسارات المحظورة.

Playwright جهّز الخادم المحلي بنجاح بعد تثبيت hostname صريح، لكن حالات المتصفح الـ70 لم تبدأ لأن Chromium `v1228` غير موجود في البيئة، وخمس محاولات تنزيل من `cdn.playwright.dev` انتهت بمهلة الشبكة. هذا **قيد بيئة اختبار** وليس نجاحًا أو فشلًا وظيفيًا؛ يجب إعادة تشغيلها في CI/جهاز يسمح بتنزيل المتصفح.

## بوابات إلزامية قبل Production

1. إلغاء وتدوير Supabase secret/service-role الذي ظهر في الأرشيف الأصلي، ثم تحديثه في مخزن أسرار الاستضافة فقط.
2. إنشاء/استعادة Staging مع backup قابل للاسترجاع، ثم تطبيق migrations **044→081 بالترتيب**. Migration 043 مطبقة Production مسبقًا ولا تعاد.
3. تنفيذ SQL compile وRLS denial وconcurrency وtransaction rollback وcron checks على Staging، وخاصة 080 و081.
4. اختبار دخول عدة حسابات Admin، الدعوة بالبريد، MFA، مصفوفة الصلاحيات، last-owner guard، login history وCSV على بيانات Staging.
5. ضبط Supabase Auth Site URL/redirect allow-list وتأكيد البريد، وResend، وSentry، وفاحص malware إلزامي للرفع المحمي.
6. تثبيت Chromium بـ `corepack pnpm exec playwright install chromium` ثم تشغيل `corepack pnpm test:e2e:public` وCloudflare runtime suite.
7. مراجعة واعتماد المحتوى القانوني وسياسة الخصوصية والاسترجاع والنصوص التجارية بواسطة المالكة/المختص.
8. تنفيذ smoke tests حقيقية لمسار الدفع اليدوي، القبول/الرفض/refund، الحجز، البريد، وتسليم الملفات المحمية.
9. نشر commit مقبول إلى Cloudflare وفق runbook ثم ضبط DNS ومراقبة الأخطاء؛ لا يُنشر ZIP مباشرة كبديل عن pipeline.

## النواقص المتبقية بوضوح

- لا توجد في هذا التنفيذ صلاحية أو مفاتيح لتغيير Supabase/Cloudflare/DNS/Resend/Sentry أو تطبيق المهاجرات؛ لذلك لم يحدث أي تغيير خارجي.
- فحص malware ما زال provider integration اختياريًا في المصدر؛ يجب جعله configured وfail-closed في Staging/Production قبل قبول رفع محتوى محمي.
- صحة الإيصال البنكي تظل قرارًا بشريًا رغم ضبط المبلغ والملكية والحالة والتدقيق.
- الاختبارات الحية للـRLS والـcron والتزامن والنسخ الاحتياطي والاسترجاع لا يمكن إثباتها من source-only.
- بعض صفحات البيانات العامة تتعمد إخفاء الفشل كحالة محتوى غير متاح لحماية تجربة الزائر؛ يجب ربطها بمراقبة Server/Sentry حتى لا يتحول عطل provider إلى صمت تشغيلي.
- Node يعرض تحذير dependency داخليًا عن `url.parse()`؛ لا توجد CVE مرتبطة في audit الحالي، ويجب متابعته مع تحديثات الأدوات.
